# GreatSage 开发与版本管理约定

更新日期：2026-09-04。

本文件描述开发流程；用户已于 2026-09-04 确认整体方案并授权开始实施。

## 1. 开始实现的条件

遵循用户给出的工作方式：大型任务先澄清需求，逐步讨论关键设计；在主要需求明确后汇总范围、设计和假设，得到整体确认后开始正式实现。

当前已进入正式开发。用户已授权使用本地 OpenRouter 配置、Ollama 和 GitHub CLI，创建并持续推送 public 仓库。

## 2. 仓库与版本管理

- 工程使用独立仓库，避免将父目录及其他项目带入提交。
- 使用已有 GitHub CLI 创建 public 仓库，计划使用与工程一致的 `GreatSage` 名称。
- 围绕可说明、可验证的变更提交，开发期间持续推送有意义的提交。
- 通过版本标签记录阶段版本；发布说明写明实际功能、配置变化、验证结果与已知问题。
- 提交记录和开发文档使用清晰描述，避免将尚未实现的规划写成已完成能力。
- 涉及行为、配置或数据格式的变更，同步更新文档与必要的迁移说明。

工程已建立独立 Git 仓库，远端创建和阶段推送随实施推进。

## 3. 配置与运行数据

- 从本地已有配置或环境变量读取 API 凭据；查找配置时避免把密钥值输出到终端或日志。
- 公共仓库提供不含真实密钥的配置样例。
- 原始录音、真实转写、个人记忆、运行数据库、日志、缓存和凭据文件置于运行数据目录，并从提交范围排除。
- API 错误、请求日志和导出记录对凭据进行脱敏。
- 用户已有 Skills 的来源目录保持不变；个人技能副本和导入配置作为本地运行数据管理，不自动提交到公共仓库。
- 在首次推送前检查暂存文件清单和凭据排除规则。

已确认原始音频默认仅作短时缓冲，可手动开启本地录音保存；转写、对话、摘要和记忆保留至删除，详细日志默认 30 天，手动录音默认 7 天，期限可配置。

## 4. 模型与语音验证

- 使用用户授权的本地 Ollama 与 OpenRouter 配置开展受控的功能和性能测试。
- 首版优先完善 API 交互链路；本地测试优先复用已安装模型，并依据实测结果选择各模式默认配置。
- 记录服务名、模型、关键参数、测试环境、样本和结果，不记录 API 密钥。
- 区分语言模型、语音识别、语音合成和嵌入模型的职责与配置。
- ASR 和 TTS 分别验证本地与云端方案，记录流式能力、语言、取消、错误及可用的用量信息。
- API 模式的本机测试不启用大型本地推理模型；普通电脑的具体资源验收基线需单独制定。
- 测试应覆盖具体剩余风险：流式取消、音源切换、转写修订、跨会话恢复、压缩与删除等。
- 用本机实测说明延迟目标的达成情况；接口连通不能代替交互质量验收。
- 增加测试仅用于解决实际风险或必要验收，不为低影响文档改动编写形式化测试。
