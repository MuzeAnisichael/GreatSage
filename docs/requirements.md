# GreatSage 首版需求与验收草案

更新日期：2026-09-04。

状态：用户已确认整体方案并开始开发；核心范围和 v0.1-plan.md 默认值为实施基线。技术细节按实际验证结果完善。

## 1. 产品目标

开发一个实时在电脑上运行的秘书 Agent。它持续接收选定来源的信息，结合上下文、长期记忆、全局 Prompt、Skills 和预设，判断是否需要回答、解释或提醒，并通过文字、语音和桌宠表现反馈。

核心质量目标：实时性、语音理解准确性、行为与输出可审计、可持续开发和优化。

## 3. 已确认的首版能力边界

首版完成回答、解释、提醒和桌宠交互。长期目标包含打开软件、修改文件、执行命令、使用工具，以及扩展电脑信息输入。

首版架构应为这些能力保留明确的扩展位置；电脑操作能力在后续版本实现。

用户已明确首版不加入定时提醒。因此首版不包含定时事项创建、日程调度、提醒列表或到期通知；基于当前听到内容和预设的主动提醒仍在首版范围内。定时提醒仅列为后续候选。

## 5. 首版性能目标

用户已接受以下目标。正式验收需固定音源、模型、语音识别／合成服务、设备、网络和测量口径。

| 交互 | 首轮目标 |
| --- | --- |
| 用户说话时 | 持续显示识别中的文字 |
| 用户说完后 | 约 1–2 秒出现首段有效回答 |
| 开启语音输出时 | 用户说完后约 2–3 秒开始播报，后续内容继续生成 |
| 用户打断时 | 约 300 毫秒内停止当前播报 |

测量建议：

- 从输入音频中的实际语句结束位置计时；另记系统检测结束的时刻，避免将轮次判断延迟排除。
- “首段有效回答”指有内容的回答，不用占位文字或“正在思考”替代。
- 语音起播记录到实际播放开始；打断记录到本地声音停止。
- 本地与云端配置分别报告实测结果；记录冷启动、热运行、失败和超时。
- 记录识别、轮次判断、排队、记忆检索、LLM 首段输出、TTS 首段音频、播放等阶段耗时。
- 延迟分位数、可接受失败率、测试样本规模和准确率阈值仍待制定。

## 6. 候选总体设计

以下为设计建议，待最终确认和技术验证。

1. 音频采集分别输出带来源与时间戳的音频事件。
2. 语音活动检测、识别和轮次管理产生临时／稳定转写事件。
3. 回应策略结合全局配置、当前对话状态与内容，产生回应或静默事件。
4. 上下文构建组合近期原文、历史摘要、相关记忆和适用 Skills。
5. 模型适配层统一处理流式输出、取消、超时、错误及服务能力差异。
6. 输出管理协调气泡、语音和桌宠状态；打断后取消过时输出。
7. 事件记录贯穿各模块，供动态日志、故障分析和来源回查使用。

服务配置建议：

- 语音识别（ASR）、语言模型（LLM）和语音合成（TTS）分别选择服务、模型和凭据，支持混合搭配。
- 默认 API 方案由本机承担采集、播放、界面和必要的数据管理，避免要求用户安装大型本地推理模型或配备独立显卡。
- 本地方案按需安装和启用；其性能按具体硬件、模型与并发工作负载报告。
- 为各阶段分别验证流式能力、语言支持、取消、错误和用量统计，不能用 LLM API 连通代替 ASR／TTS 验证。
- 故障处理提供明确状态；只有用户配置了备用服务时才进行相应切换，避免未经配置切换数据处理位置。
- 本地和云端的输入、响应及事件记录采用统一格式，保持记忆与审计的一致性。

Skills 加载建议：

- 索引技能名称、描述、来源和版本；按需加载正文及相关参考资料，并纳入上下文预算。
- 记录每次回应实际选择的 Skill、加载的资源与内容版本，支持回查。
- 保留用户原有技能文件；导入记录、个人技能副本和路径配置作为本地运行数据管理。
- 明确展示技能依赖及当前可用能力；依赖脚本、外部服务或工具的部分在首版不能视为已支持。
- 技能资料不能自动改写全局配置；与全局指令及明确设置的具体优先规则在预设设计中确定。

需要重点验证：应用音源重启后的选择恢复、麦克风与系统声音重复收录、助手自身语音回流、连续旁听期间的插话时机、打断后的历史一致性。

## 7. 审计设计建议

每次交互使用关联标识连接以下内容：

- 输入来源、时间范围、转写状态／修订和证据引用。
- 生效的全局预设、Prompt、Skill 和相关配置版本。
- 触发事件、匹配条件，以及回应／延迟回应／保持静默的结果。
- 注入模型的上下文组成、摘要版本和记忆来源。
- 模型服务、模型名、参数、耗时、用量（服务提供时）、错误和重试。
- 生成的文本、实际显示／实际播报范围、取消与打断记录。

记录可检查的输入与决策结果；不将模型生成的自我解释视为真实内部推理或审计证据。

默认需要排除凭据，并避免将原始私人运行数据纳入公共仓库。原始音频默认仅作短时缓冲，可手动开启本地保存；开启录音后的保存期限、日志保存期限及完整调用内容记录方式待确认。

## 8. 启动实现前的整体确认

核心功能范围已逐项明确。界面组织、默认语言、预设优先级、数据保存期限及开发起步方式集中记录于 [v0.1 整体方案确认稿](v0.1-plan.md)，作为一组建议默认值提交确认，避免继续逐项询问低影响细节。

具体 ASR／TTS 服务、模型、技术依赖和可量化的准确性／资源基线在获准启动后通过有界技术验证确定，并记录依据。它们不能削减本地与云端均支持、API 优先及已确认交互功能等要求。

整体方案已于 2026-09-04 得到用户确认，正式开发已启动。
