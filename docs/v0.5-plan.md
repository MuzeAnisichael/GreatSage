# v0.5 语音实时性与 Windows 安装方案

确认日期：2026-10-21。用户确认按本方案推进，并允许增加可选专用流式语音服务。阶段方向见[路线图](roadmap.md)；当前进入分片实施，完成与验证状态随开发日志记录。

基线为已发布的 `v0.4.0-alpha.1` / `main` 提交 `a624bfd`，本地与 GitHub 一致。历史结果见 [v0.4 验证](validation-v0.4.md)，不能作为本版本的语音或安装验收结果。

## 已确认的目标与约束

- 本机 Windows 优先，面向普通个人电脑，API 优先，同时支持本地 ASR、Ollama 和系统 TTS；识别、模型与合成独立配置。
- 保留麦克风、系统整体及指定进程音频的来源身份，保留三种回应模式、全局指令、只读 Skills、记忆、工具审批与桌宠。
- 先补齐可比较的语音指标，再逐片评估并迁移 Pipecat；随后完成 Windows 安装、升级、卸载和数据保留。
- 继续小切片提交、同步日志和代码导航，经检查后交付 main。复用现有评测和 CI，只补当前风险需要的检查。

## 当前缺口与设计依据

现有 `Providers.transcribe()` 发送分段音频；`Providers.synthesize()` 收齐一句音频后返回。仅替换编排框架不会自动获得原生流式识别或边生成边播放。

现有基准脚本记录音频就绪，但未测实际起播。前端 `AudioPlayer` 已有播放回执，首先复用它补齐计时、回应代际和回执顺序；静态审查发现 `Runtime.playback()` 的迟到回执隔离需要核实，目前尚未复现为缺陷。

采用 [Pipecat](https://github.com/pipecat-ai/pipecat) 的语音处理组件和服务适配，保留 GreatSage 的 Windows 采集、来源、权限和审计边界。实施前核对并固定可兼容版本及许可证，优先薄适配，避免长期维护两套完整管线。

## 验收口径

- 2026-10-22 用户调整优先级：先完成功能，不强行达到预设数值。首字、起播与打断目标作为后续优化参考，不阻塞独立功能开发和阶段推进；权限、数据保留、隔离与失败处理仍须验证，未测的设备／安装／真实服务能力仍明确标注。
- 分开记录：语音实际结束、VAD 结束、最终识别、模型有效首字、音频就绪、客户端实际起播、打断停止。标注冷／热状态、服务、样本、费用与资源。
- 沿用首字约 1–2 秒、实际起播约 2–3 秒、打断约 300 ms 内的目标；先测量，再报告达标或差距，不因框架迁移承诺性能。
- 停止监听、切换会话、取消或删除来源后，迟到识别、模型、合成及播放回执不能写回或改变新状态。
- 故障恢复不自动改用另一家服务；保留配置、来源与审计信息。外部工具仍经过原审批和未知结果账本。
- 安装验收确认实际程序启动和退出、单实例、托盘及后端清理。目录包组件检查不能替代安装 EXE 验收。

## 安装侧建议默认值

当前用户安装，沿用应用身份与既有数据路径；手动下载升级，卸载保留数据，安装完成后由用户启动。暂不增加开机启动、自动更新或购买签名证书。

升级／卸载不得清除历史、记忆、SQLite/WAL、图 checkpoint、配置及密文引用、用户 Skills、录音或工作目录。本轮不顺带搬迁数据目录；DPAPI 仍遵守 Windows 用户绑定。退出验收需确认业务关闭与数据落盘，不能仅检查子进程消失。

## 2026-10-21 确认的服务范围

**用户已允许将一个可选的专用流式语音服务纳入 v0.5。**

先用现有 OpenRouter／本地服务建立基线，再根据中文理解、时延、费用和 Pipecat 适配情况选择一个服务；这可能需要额外账号／密钥。现有接口继续可选，不自动跨服务转交音频。服务选择与接入配置另行记录；仅在用户明确选择且配置凭据后启用，不代替用户注册账号或购买服务。

没有新服务凭据时，可以完成接入与隔离协议验证，真实服务时延与识别质量保留为未测；继续推进现有服务、播放与安装等不依赖该凭据的工作，不编造通过结果。

LangMem／实体记忆、产品多 Agent、屏幕理解和定时提醒仍按后续路线图安排。

## 2026-10-22 功能完善切片

本轮先补单音源识别恢复：采集仍在运行时，用户可单独重试失败的识别管线，保留其他音源；新连接只处理重试后的音频，清理旧片段和异步结果。首页及运行监控持续显示故障原因、设置入口和恢复动作。设备／进程采集停止仍需检查来源并重新开启监听，不把重建识别连接描述为修复设备。复用现有 Pipecat／官方 SDK，不增加自动重连、重放或服务回退。

## 已选择的实现与边界

- [Pipecat](https://github.com/pipecat-ai/pipecat) 1.13.0（BSD-2-Clause）提供音频帧、串行处理、生命周期及官方 STT 适配，采用当前 `PipelineWorker`／`WorkerRunner`。保留本项目 WebRTC VAD、Windows 音源身份、回声门控和权限规则，不另写完整传输框架。
- 可选服务采用 Deepgram Nova-3、[官方 SDK](https://github.com/deepgram/deepgram-python-sdk) 7.14.0（MIT）。[官方模型说明](https://developers.deepgram.com/docs/models-languages-overview/)列出中文及所需语言，Pipecat 已有对应适配；这支持先实现薄接入，不能替代本机中文质量、费用与实时性比较。当前尚无新服务凭据。
- 仅允许初始地址 `https://api.deepgram.com`、`nova-3`／`nova-3-general`、`zh`／`zh-TW`／`en`／`ja` 及常见别名；默认 `zh`。使用 `DEEPGRAM_API_KEY` 或明确保存的新密钥。失败不自动重连、重放或换服务，需用户重开监听。SDK 内部 TLS 重定向沿用上游，不能将初始地址限制描述为禁止所有重定向。
- API／本地分段识别继续可选，TTS 仍为分句合成。流式服务的 `is_final` 只表示稳定片段，需本地 VAD 结束与远端端点确认同时满足才进入既有记忆／回应入口。
- 队列积压、15 秒仍无 Finalize、新话轮早于上一话轮确认、无效时间区间或超大转写会停止相应流式音源并提示重开。初版选择明确失败而非猜测话轮归属；自然连续说话的适用性仍待真实服务验证。
- 原始录音默认关闭；开启时流式话轮仅保留最长分段配置范围内的 PCM，超过范围不保存残缺录音，文本和跳过原因仍可追溯。
- 默认仅本地结构化日志，关闭框架转写日志、RTVI 和远端追踪；仅在开启监听且明确选择服务后发送所选音源。连接探针不发送音频。
