## 1. 已确认范围

| 项目 | 首版交付 |
| --- | --- |
| 定位 | GreatSage（大贤者），实时在电脑上运行的语音秘书 |
| 平台 | 以用户当前 Windows 11 电脑开发和验证，后续再做其他环境兼容 |
| 输入 | 麦克风＋一个桌面音源；桌面音源在系统整体和指定程序之间选择，分别转写与标注来源 |
| 理解与回应 | 聚焦人的语音；支持对话、旁听问答、主动解释和内容触发提醒，由全局指令与预设控制 |
| 模型与语音 | ASR、LLM、TTS 均支持本地与云端，优先完善 API 方案，照顾普通个人电脑配置 |
| Skills | 直接复用现成 SKILL.md 目录，导入、启停、按需加载指令与参考资料 |
| 记忆 | 长期、跨会话、近期原文、分层摘要、历史检索、显式记忆、来源回查、修正／删除、上下文压缩 |
| 日志 | 持久化与动态显示，关联输入、触发、配置、模型调用、上下文、输出及各阶段耗时 |
| 输出与桌宠 | 多语言文字／语音、可打断、Q 版形象、摸摸、对话气泡与基础动画 |

首版不包含定时提醒、电脑操作、技能脚本／外部工具执行、非语音声音识别或多程序分别监听。后续能力见 [路线图](roadmap.md)。

## 2. 关键设计

### 音频与模型处理

采用分层的桌面客户端和后台处理模块：音频采集 → 转写与轮次判断 → 回应策略 → 上下文／记忆／Skills → LLM → 文字、语音和桌宠。

统一事件记录贯穿处理过程。ASR、LLM、TTS 分别配置服务与模型，支持本地／云端混合搭配。API 默认运行路径不依赖大型本地推理模型；本地组件按需启用。

将音源标记、助手语音回流处理、转写修订和打断取消作为核心行为验证，防止重复回应或继续播放过时内容。

### 主动回应

监听持续进行，只有满足当前预设的触发条件才产生回应。触发检查结合稳定转写、当前说话／播放状态与可配置的频率限制，避免对每个临时转写片段重复启动完整生成。

触发结果可为立即回应、延迟到当前发言结束或保持静默。延迟是为等待当前对话合适时机，不引入定时事项和日程调度。

### 记忆与压缩

保留近期原文，用分段／会话摘要压缩较早上下文，按当前问题检索历史。摘要记录来源区间和版本，精确细节可回查原文。修正／删除同步影响派生摘要、索引和缓存。

上下文按模型容量预算构建；后台压缩优先让出前台对话所需资源。详细候选设计见 [记忆方案](memory-design.md)。

## 3. 已确认的默认值

| 项目 | 建议 |
| --- | --- |
| 界面 | 主控制台负责设置、聊天、记忆和动态日志；独立桌宠窗口负责日常陪伴、气泡和简单交互 |
| 桌宠 | 首版使用可替换的原创 2D Q 版素材与基础状态动画；复杂 Live2D／3D 表现后续评估 |
| 语言 | 界面默认简体中文；输出提供中文、英文、日文预设，文本与语音语言可配置；具体声音随所选服务配置 |
| 初始行为 | 默认启用对话秘书预设；另提供旁听助手、主动秘书预设，均可编辑保存 |
| 配置边界 | 明确设置优先于全局指令，全局指令优先于 Skills；桌面音频默认作为待理解内容，Skills 和被监听内容不能自行改写设置 |
| 主动发言 | 用户当前发言优先；允许配置最小发言间隔、免打扰和触发条件，支持内容去重；具体初始参数通过样例验证确定 |
| 打断 | 麦克风检测到有效语音时默认停止当前播报并取消过时输出；需要结合助手自身声音回流处理验证 |
| 历史与记忆 | 转写、对话、摘要和显式记忆默认保留至用户删除；磁盘用量可见，并提供清理入口 |
| 详细日志 | 默认保留 30 天，保存期限可调整；保留范围变化时明确对审计回查的影响 |
| 手动录音 | 默认关闭；开启后的录音默认保留 7 天，保存期限可调整 |
| 服务异常 | 明确展示错误和当前状态，仅使用用户已配置并启用的备用服务；没有可用备用时暂停受影响环节 |

以上默认设计已随整体方案确认，不代表每项均已实现或验证。后续变更同步文档与实际实现。

## 4. 性能与正确性

已确认首轮目标：

- 说话时持续显示识别文字。
- 说完后约 1–2 秒出现首段有效文本。
- 说完后约 2–3 秒开始语音播报。
- 打断后约 300 毫秒内停止播报。

本地与云端配置分别实测，报告全链路和各阶段延迟、错误和资源使用。核对代表性语音的转写与问答、跨会话回忆、压缩后的精确检索、修正与删除一致性。

具体服务／模型的结果以测试为准，不将接口连通、占位提示或桌宠动画当作有效响应验收。

## 5. 获准启动后的实施方式

1. 建立独立工程、公共 GitHub 仓库、配置和运行数据隔离、提交与文档维护流程。
2. 以有界技术验证确定桌面框架、Windows 音频接入与 ASR／TTS 适配，记录选型依据。参考 AIRI、Open-LLM-VTuber、Pipecat 的相关设计；是否直接依赖具体框架根据验证结果确定。
3. 优先跑通 API 实时闭环，再补齐本地／混合配置、回应策略与记忆。
4. 完成桌宠、控制台、审计视图和验收，按阶段推送并发布版本标签。

具体库、服务和模型的选择由开发验证解决；若验证结果要求改变已确认的产品范围或数据处理方式，再回到需求讨论。首版内部演示不能替代全部已确认功能的交付。
